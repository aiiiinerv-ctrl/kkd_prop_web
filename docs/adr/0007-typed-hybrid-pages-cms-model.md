# Typed hybrid data model for the fixed-template Pages CMS

The Pages CMS uses a code-owned six-page registry, extends the existing `PageSeo` records for shared typed Properties, and stores each page's fixed-template Content in its own typed singleton with normalized child rows for FAQs and Featured References. We rejected a generic `Page` record with JSON content because it would weaken database constraints, field-level audit readability, and page-specific evolution; we also rejected wholly independent per-page models because duplicating Properties would break the existing ten-row SEO/legacy Settings boundary. Reusable Service, Package, Portfolio Project, and Testimonial records remain their own Content Items, and no Media Asset abstraction is introduced for one OG image per page.

This model depends on InnoDB in production: Foreign Keys, optimistic aggregate saves, and the mutation-plus-Audit-Log transaction are release invariants, not application-only conventions. Production must therefore be converted from MyISAM and verified before Pages CMS writes are enabled. Schema rollout is additive and backfilled before page-by-page cutover; rollback reverts application reads while retaining the new tables and data through the compatibility window.
